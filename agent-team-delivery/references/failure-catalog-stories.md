## 儀器與環境——量到的不是你以為的東西

### [stale-cache] 舊的快取 / 舊的 origin  (原 5.1)

有 service worker 的站台,快取優先的 shell 會在你以為在看新版時餵你舊版。
加 query string **不一定**能穿過(cache 可能 `ignoreSearch`)。

- 驗改過的 JS/CSS,要用**全新的 origin**(換 port),不是重新整理。
- 在瀏覽器裡量任何東西之前,先讀一個**版本戳記**(例:`window.__build`),
  跟你剛 ship 的比對。
- `curl` 沒有 service worker,是判斷「origin 到底送出什麼」的裁判。

> 同一個 session 裡,我先正確地把一個異常數字診斷成「舊快取」,二十分鐘後
> 又在同一個瀏覽器上量另一個頁面,完全沒想到要套用同一條。
> **診斷出一個陷阱,不等於下一次會避開它。**

### [someone-elses-server] 量到別人的伺服器  (原 5.14)

[stale-cache] 是「舊的快取」;這是它的鄰居:**你的 server 根本沒起來,而那個 port 上
有別人的東西。**

真實案例:我在背景起了一個靜態伺服器,它因為 port 被另一個 session 的 dev
server 佔用而**靜默失敗退出**;我接著對那個 port 量了好一陣子,量到的是另一
個專案的網站。第一個徵兆是一個莫名其妙的 404。

多 session 同時工作時,port 是共用資源,而背景任務的失敗你不會立刻看到。

**判準:量之前先證明那個 origin 是你的。** 種一個只有你的 build 會回傳的
標記——一個檔案、一個版本戳記、一個你剛改過的常數——先讀它,再開始量。

### [synthetic-events] 合成事件不是真的互動  (原 5.7)

- `el.click()` 送出 `detail: 0`,那是 **Enter 鍵**的簽名,不是滑鼠點擊。
- 合成的 tap 不會產生 hover,所以用它做的 guard 對 `:hover` 分支毫無證據力。

### [hidden-pane] 隱藏 / 不合成的 pane  (原 5.8)

計時器被節流、有限動畫永遠不會結束(`await animation.finished` 因此永不
解析)、`innerWidth` 讀到 0。症狀是「跑很久像當掉」或「一堆莫名其妙的失敗」。

**而且解法本身會製造新的假失敗**:我裝了一個每 100ms 送 keydown 的
「解卡幫浦」,結果它把正在斷言「必須等待玩家按鍵」的測試全部弄紅。

### [measure-the-container] 量到容器,而不是量到東西本身  (原 5.9)

- 縮放自適應的元素,量它自己的 rect,永遠回答「放得下」。要量**容器**。
- 從靜態 HTML 推算高度,會漏掉 **JS 載入後才掛上的元素**(一個語言切換鈕
  就值 69px,足以讓兩份仔細的量測差出一整個結論)。

### [rounding-at-threshold] 儀器裡的四捨五入，正好磨掉了門檻要分辨的那一位  (原 5.15b)

一個 peer 的色距檢查最後一行是 `+Math.sqrt(...).toFixed(2)`,而它的判準是
「兩兩色距 **≥ 12**」。真值是 **11.9988**,`toFixed(2)` 給出 **12.00**,於是它
回報「最小間距 12.00,通過」。

**那個儀器在物理上不可能分辨「剛好 12」和「差一點點不到 12」。** 它不是量錯,
是**把答案四捨五入到剛好抹掉門檻所在的那一位**。而回報出來的 `12.00` 看起來
比 `11.9988` 更像一個乾淨的通過。

是另一個實作用不四捨五入的算法重算才發現的。順帶一提,兩個獨立實作給出
11.9974 和 11.9988——**差在第 3 位小數,到第 2 位一致,那是互相佐證不是矛盾**;
真正的問題是那個 `.toFixed(2)`,不是兩者的差。

**判準:任何「≥ 門檻」的檢查,格式化只能發生在最後印出來的那一步,不能發生
在比較之前。** 更一般地:**問你的儀器的解析度,跟你的門檻差幾個數量級。**
兩者同級的時候,「剛好通過」和「剛好不過」會被印成同一個字串。

順帶一個相鄰的形狀:**度量的分母也要跟兩端一起固定**。同一段時間、同一個
畫面,我量到「蓋住畫布 18.7%」而 peer 量到 13.9%,兩邊的**分母逐字相同**
（同一個 canvas 矩形）——差的是**分子**:那個容器是 `width:max-content`,
而我們兩個探針餵進去的字串長度不同。**同一支儀器、同一個公式,不同的輸入,
就不是同一個量。** 而同一次量測裡的另一個數字（整疊高度 179px)兩邊逐字相同,
因為它不隨字串長度變——**挑那個當 guard 的斷言對象。**

### [pipe-eats-exit-code] pipe 吃掉 exit code  (原 5.10)

```bash
cmd | grep FAIL; echo $?      # 這是 grep 的狀態,不是 cmd 的
cmd > /tmp/out.txt; echo $?   # 這才是
```

**同一族的第二個:`&&` 鏈裡的一步失敗了,而 `;` 後面的那一步照常執行。**

真實案例,而且很難看:我為了證偽,故意把一個缺陷注進檔案;證偽成功之後,
還原那一步寫在 `cp 備份 目標 && grep 檢查` 的鏈裡——**備份路徑打錯,`cp` 失敗,
`grep` 沒跑**;而 `git commit` 用 `;` 接在後面,**照樣把帶著注入缺陷的檔案提交了**。

我在同一個小時裡才剛把「清理要放在下一次使用前的前置檢查,不能只放在這一次
結束時的收尾」寫進這份文件([cleanup-as-precondition])。**然後用一個 shell 的 `;` 演示了一次。**

**正確的形狀不是「commit 之前記得還原」,是「樹上還有 FALSIFY 標記就不准 commit」**
——一個前置條件,不是一個步驟:

```bash
grep -c FALSIFY file | grep -q '^0$' && git commit ...   # 檢查通不過就不會 commit
```

判準:**任何「注入 → 觀察 → 還原」的流程,還原都不能是鏈上的一步。**
把「乾淨」寫成下一個動作的守衛,因為鏈會斷,而斷掉的鏈不會攔住 `;` 後面的東西。

**而最陰的一種:`grep -c` 在計數為 0 時離開碼是 1——而 0 正是「好」的結果。**

```bash
git show HEAD:a.js | grep -c '壞東西' && git show HEAD:b.js | grep -c '壞東西'
#                                    ↑ a.js 乾淨(印 0、exit 1)→ 鏈斷 → b.js 從來沒被檢查
```

**驗證鏈恰恰在一切正常的時候斷掉**,所以它的失敗方向是「安靜地少驗了幾個檔案」,
而你看到的是一個 `0` 和沒有錯誤。同一個 session 裡我踩了兩次、一個 peer 踩了一次。

寫法:把每一項分開跑、各自印出來,不要用 `&&` 串「檢查」——
`&&` 是給「前一步成功才做下一步」用的,不是給「逐項檢查」用的。

```bash
echo "a: $(git show HEAD:a.js | grep -c '壞東西')"
echo "b: $(git show HEAD:b.js | grep -c '壞東西')"
```

## 假綠——guard 本身是死的

### [circular-expectation] 檢查從被檢查的東西身上取得期望值  (原 5.2)

最常見、最難看見的一種假綠。

- 從 INSERT 語句取出欄位清單,再用同一份清單讀回來 → 把兩個欄位對調會
  **互相抵銷**,測試沉默通過。
- 期望值由被測資料推導 → 你測的是資料的形狀,不是規則。

**判準:如果我把規則改錯,期望值會不會跟著一起錯?** 會的話,這條檢查沒有用。
期望值要另外手寫、獨立敘述那條規則。

### [verify-in-working-range] 在能運作的區間驗證儀器  (原 5.3)

我曾用「這一欄完全線性」來證明我的量測方法可靠——但**線性的那一欄是溢出
的區間,而故障只存在於「裝得下」的區間**(`min-height:100vh` 讓任何裝得下
的頁面都回報 0)。

> 在能運作的那一半驗證儀器,對壞掉的那一半什麼也沒說。

**判準:提出一個驗證時,先說出它取樣了哪個區間、總共有哪些區間。**
只要路徑上有任何「飽和 / 夾限 / 釘死」的機制,它造成的邊界**就是**區間分界。

### [name-promises-more] 名字承諾得比斷言多  (原 5.5)

測試叫「a wall move costs nothing, **and a legal one still costs a turn**」,
但合法那半只斷言了位置、記錄、事件,**從來沒有斷言回合**。
稽核覆蓋率的人讀名字、打勾、不會打開內容。

**要嘛補斷言,要嘛改名字。**

### [nonempty-population] 對缺席的主張,要先證明現場非空  (原 5.6)

「按了牆壁什麼都沒發生」——如果當下**沒有牆可以按**,這條測試永遠通過。

```js
assert(walls().length > 0, "沒有牆可撞,這條 guard 從來沒有試過");
```

任何「必須不包含 / 必須沒有改變」的檢查,都要先斷言它讀取的區域非空。

### [unfalsified-guard] 逃過證偽的 guard,不是隨機抽樣  (原 5.15)

**你會去證偽哪一條 guard,跟哪一條 guard 需要被證偽,是負相關的。**

真實案例:一週之內我證偽了輸送帶的 guard、存檔的 guard、品質倍率的
guard——每一條都親手弄紅過。唯獨沒有證偽「`tick()` 不得碰 DOM」那一條。
它是整個前後端邊界的唯一守門員,是之後抽出 `sim.js` 時唯一的依據,而且是
我**反覆引用給兩個 peer 聽**的那一條:「它會咬你,不只是唸你。」

它從第一天起就不可能紅。`mo.takeRecords()` 會把佇列**排空並回傳**,而
MutationObserver 是非同步派送的——同步跑完一圈 tick 之後 callback 還沒
執行,所有紀錄都還在那個被我丟掉的回傳值裡。實測:**500 次真實的 DOM 屬性
異動,guard 回報 `0`,測試全綠。**

是 peer 在自己的區域裡放了一個 DOM 寫入、預期會紅、結果是綠,才發現的。

為什麼偏偏是這一條?因為:

- 它是**地基**。地基「顯然」是對的,不然上面的東西早就垮了——這個推論是
  假的,但它非常有說服力。
- 它太便宜。一行 `0 mutations` 綠得毫不費力,不像會出事的樣子。
- **我一直在引用它。** 引用一條 guard 的感覺,跟使用一條 guard 的感覺,
  幾乎一樣;而引用不會執行任何東西。每引用一次,它就更像是已經被驗證過的。

**判準(問順序,不要問清單):不要問「我證偽過哪些?」,要問「我沒證偽過
哪些,為什麼跳過它們?」** 理由若是「它太基礎了」「它一直是綠的」「我都拿
它當標準在講」——那正好就是下一條要弄紅的。

順帶一個一般性的陷阱:**排空型的 API(`takeRecords`、`splice`、`drain`、
`poll`)把「清空副作用」和「取得資料」綁在同一次呼叫裡。** 只當它是清理而
丟掉回傳值,量測就被丟掉了,而且不會有任何錯誤——留下的是一個永遠回報零的
儀器。

### [red-capable-vs-alive] 「能紅」不等於「這一次是活的」  (原 5.16)

修好一條不可能紅的 guard 之後,我用兩種方式證偽它。第一種:讓產品去寫
DOM——紅了,`500 mutations`,很好。第二種:把 observer 指向一個剛建立、
沒有掛進文件的 `<div>`——**綠了,`0 mutations`**,和一次乾淨通過完全
無法區分。

**「這條 guard 有能力紅」是程式碼的性質;「這條 guard 這一次瞄準了正確的
東西」是那一次執行的性質。** 只有後者才讓你有資格把一個 0 當成證據。

每一條「不存在」的主張都有這個無聲的失敗模式:儀器正在觀察一個空的宇宙。
瞄錯目標、提早 disconnect、節點是 detached、選擇器選到空集合——結果都是
一個充滿自信的零。

**判準:把存活證明放進 guard 本身,而不是放在另一次證偽裡。** 故意製造一次
違規,要求 guard 看見它;或先斷言母體非空([nonempty-population])。另一次跑過的證偽只證明它
「曾經」有效,不證明它「今天」瞄得對。

### [cleanup-as-precondition] `try/finally` 擋不住「呼叫被殺掉」——清理要放在下一次的開頭  (原 5.16b)

一個 peer 為了量測,暫時把一個欄位注入產品的資料表,用 `try/finally` 還原。
兩次量測**逾時被中止**,`finally` 沒有執行,那個欄位就一直留在正規的資料表上
——**下一次量測的「基準線」是被污染的**。

救它的是它放在**每次量測開頭**的一句斷言:「這張表現在是乾淨的嗎?」
那句斷言真的紅了兩次。

**`finally` 保證的是「這一次正常結束時會收尾」,不是「下一次開始時是乾淨的」。**
逾時、中止、行程被殺、瀏覽器分頁被搶走——每一種都會跳過它。

**判準:清理要寫成「下一次使用前的前置檢查」,不能只寫成「這一次結束時的收尾」。**
這跟 [red-capable-vs-alive] 是同一個家族:那一條說「能紅不等於這一次是活的」,這一條說
**「上一次有收尾」不是一個可以假設的事實,它是一個要被檢查的事實。**

而那句開頭的斷言不是防禦性程式碼,它是一個**存活對照**——它讓「基準線乾淨」
從被假設變成被驗證。

### [green-path-unseen] 為「綠色也要看得見」而寫的訊息,你看過綠色那一列嗎  (原 5.21)

我在 harness 裡寫了好幾條**專門為了通過時也印出數字**的訊息——配件色目前的
最小值與「12 以下幾組」(為了讓侵蝕看得見)、最長空窗幾天、貼著門檻的有幾張。
侵蝕本來就是靠這些數字被發現的。

`ok(cond, msg)` 是 `return cond ? true : msg`。**通過時訊息直接被丟掉。**
48 條 check 以 `return ok(...)` 收尾,**它們的訊息一次都沒有顯示過。**

我還在交付訊息裡寫過「第 19 組即使全綠也會印出目前最小值」——**一句我從來
沒有親眼確認過的話。** 我看過那一列是綠的,沒看過它印了什麼;而「它是綠的」
和「它印出了它量到的東西」是兩件事。

**判準:凡是你為「通過的情況」寫的輸出,去看一次通過的那一列。**
紅色的路徑天天有人走(每次證偽都走一遍),**綠色的路徑沒有人看**——
而追蹤緩慢侵蝕的數字,永遠長在綠色的路徑上。

一般化:**失敗路徑會被證偽測到,成功路徑不會。** 任何只在成功時執行的程式碼
(通過訊息、成功後的清理、"nothing to do" 的分支)都要另外找一次機會看它跑。

### [guard-punishes-completion] 一條會懲罰「把工作做完」的 guard  (原 5.24)

我在 harness 裡放了五張**背債表**(已知的、有主的、暫時放行的違規),每一張都配
一條檢查「表上的都還存在、都寫了理由」。五張我都寫了 `nonEmpty(表的大小)`。

於是:**把最後一筆債還完的人,會把 harness 弄紅。**

一個 peer 被我叫去刪掉最後一筆時發現的,它的話很精準:
**「刪了一定會紅,不刪反而不會。」**

那是 [nonempty-population] 的誤用。[nonempty-population] 說的是「**你掃描的母體**不可以是空的」——沒有牆可以撞的
時候「撞牆沒事」永遠通過。**它不是說「你的例外清單不可以是空的」。**
背債表空掉是**目標狀態**,不是儀器故障。

**判準:對每一條 guard 問一次「把它守護的東西做到完美,它會變成什麼顏色?」**
答案必須是綠的。如果理想狀態會讓它紅,那條 guard 就在跟它自己的目的作對——
而且會**教下游不要把事情做完**,那是最貴的一種錯誤誘因。

同一個形狀的其他版本:要求「至少有一個 TODO」、要求覆蓋率報告非空、
要求 changelog 每次都有新條目。**任何「數量必須 > 0」的斷言,先問那個 0 是不是勝利。**

### [product-verb] 這個產品的動詞是什麼?哪一條檢查會因為它停擺而紅?  (原 5.27)

[unfalsified-guard] 說「逃過證偽的 guard 不是隨機抽樣」。這是它的極端版:**那條 guard 從來沒有被寫過,
而它缺席的地方,正好是所有人都假設有人在看的地方。**

一個 peer 在修調度的缺陷時,做了一版**刻意過度積極**的錯誤修法(「車上有人就誰都不接」),
然後跑驗收:**72 pass / 0 fail,全綠。** 它回報給我。我複驗,並量了代價:
那個版本的送達率**比不修還糟 7.7 個百分點**,三種配置全部下降。

七十二條檢查守的是內容資料、顏色、形狀、翻譯、提示、事件池。
**沒有一條在問「這台電梯有沒有在送人」——而那是這個遊戲唯一的動詞。**

為什麼會這樣,值得說清楚:

- **周邊比核心容易寫。** 「每個 id 都有英文」是一條 grep;「調度還能用」要跑模擬、
  要選配置、要挑門檻。**於是 guard 長在容易長的地方**,而數量會讓人以為覆蓋率也長了。
- **核心「顯然」有人看。** 它壞掉的話遊戲會很明顯地爛掉——這個推論是假的
  (壞 7.7 個百分點不會讓任何東西看起來壞掉),但它非常有說服力。
- **我兩天內在這份 harness 上加了六條、修了四條,一次都沒問過「送達率有沒有人在看」。**
  往一個地方加東西的動作,會讓人覺得整體變強了。

**判準:問「這個產品的動詞是什麼?」然後問「哪一條檢查會因為那個動詞停擺而紅?」**
如果答不出第二題,先寫那一條,再回去補周邊。

寫它的時候門檻要**鬆**:它抓的是崩塌不是漂移。貼著實測值的門檻會在每次加內容時變紅,
而那種 guard 最後會被人註解掉——**一條被註解掉的 guard 比沒有更糟,因為它還在檔案裡
假裝有人在看**。把實測值印在通過訊息裡(見 [green-path-unseen]),漂移交給眼睛。

### [dead-branch-fix] 一條在今天的資料上永遠不執行的修正,會通過所有測試——因為它什麼都沒做  (原 5.28)

我開了一張 issue,指定判準是「跳過**永遠**裝不下的乘客」,寫成 `p.t.size > cap`。

peer 沒有照著寫,它回報:**最小載客量 4,全表最大的 size 也是 4。`4 > 4` 是 false。**
照字面實作會得到一條 `continue` 永遠不執行的修正,**而它會全綠,因為它什麼都沒改**。

這是 [nonempty-population](對缺席的主張要先證明現場非空)的**規格版**:
[nonempty-population] 講的是「檢查」的母體可能是空的,這一條講的是「**修正**」的母體可能是空的。
兩者的症狀相同——一片綠——但這一次綠的是產品,不是儀器。

**判準:寫下一個條件之後,先問「今天有幾筆資料會讓它成立?」** 答案是 0 的話,
你交出去的是一個**永遠不會執行的分支**,而測試沒有辦法告訴你,
因為「沒有東西改變」正是它預期的結果。

⚠ 我去複驗 peer 這個說法時,grep 到兩個 `size:6`,有一瞬間以為它算錯了——
**兩個都在註解裡**。「在原始碼文字上比對會把註解當資料」是我親手寫進每一份 brief 的
那一條,而我在同一天的驗證裡踩到它兩次。**寫進 brief 不會讓你自己免疫。**

## 取樣與數字

### [discriminating-points] 取樣要取「能分辨的點」,不是方便的點  (原 5.12)

設計文件會自己跟自己矛盾——同一節裡同時寫著一條**公式**和一張**表格**,
而兩者只在某些點上不同。

真實案例:一份設計文件同時寫著一條乘數公式和一張三列的對照表。兩者在**前
兩列給出相同的答案**,只有第三列(區間的一端)不同。於是三列裡有**兩列替
錯誤的公式背書**,而它活過了兩個版本的設計文件——每個讀過的人都抽樣過,
只是都抽在一致的那兩點上。

> 在方便的點取樣,會**確認**一個 bug。

**先問:哪些點能分辨這兩種解釋?只在那裡取樣。** 而且當文件裡有 N 個地方
描述同一件事,不要挑一個信——**全部列出來,看誰跟誰一致**。少數的那個通常
是錯的,但要數過才知道誰是少數。

### [initial-state-sample] 取樣點裡有沒有「系統的起始狀態」?  (原 5.26)

[discriminating-points] 說「在方便的點取樣會確認一個 bug」。這是它最常見的一個實例,而且值得單獨記:

我寫了一條掃三種規模的 guard(小/中/大),挑的是 12 / 30 / 80。**而系統的起始值是 5。**
我挑的「小」不是真正的小,是我覺得像小的那個數字。一個 peer 去量了 5–10,
在那裡找到一個超過門檻的違規——**那正是每一個玩家都會經歷的狀態**,
而且是**唯一一個所有人保證都會經歷的狀態**。

更糟的是它反過來也成立:我後來把違規的那一列修好,**在 5 層量到的違規程度
(25.5%)比我原本取樣的任何一點都嚴重**。三點取樣不只漏掉了它,還漏掉了最糟的那一個。

**判準:取樣的清單裡要有「預設值 / 初始值 / 空的那一個 / 第一次執行」。**
那些點通常不在你憑直覺列出來的等距序列裡,而它們是母體裡權重最高的——
每個使用者都從那裡開始,只有一部分人走到你取樣的其他點。

同一族的其他遺漏:第一次執行(沒有快取、沒有存檔、沒有歷史)、
空清單、單一元素、剛好在邊界上的那一個。

### [grid-count-not-absolute] 取樣密度下的計數,不要當成絕對值報出去  (原 5.22)

我裁決一個顏色門檻時寫:「門檻 9 只剩 **1,639** 個可行點」,並在同一段講
「加兩三個顏色就會塌」。那個 1,639 是 **step 4(每軸每 4 個值取一個,
262,144 個取樣點)** 的計數。全解析度是 **111,110**,而比例兩邊都是 0.6%——
**兩次量的是同一件事,錯的是我引用它的方式。**

代價不是那次裁決(門檻 9 本來就是對的),是**那句話被我寫進了後面每一份
brief**:「顏色空間快用完了,新型別越少越好」。一個 peer 差點照著一個
不存在的限制去規劃,是它自己去掃了全解析度才發現的。

同一個粗網格還讓我說出「藍色完全不存在」——實際上門檻 9 有 1,864 個藍點,
**它在門檻 10 才歸零**。粗網格漏掉的是薄的那一條帶,而薄的帶正是你會想知道
它在不在的那一種。

**判準:凡是從取樣網格數出來的計數,報出去的時候要嘛換成比例、要嘛把網格
寫在同一句話裡。** 「1,639 個點」和「0.63% 的空間」是同一個事實,而前者會
被下游當成一個小到危險的絕對數量——**尤其當它被寫進別人的 brief 的時候。**

附帶:**「完全沒有 X」這種主張對取樣密度特別脆弱。** 粗網格上的 0 只代表
「這個網格沒踩到」,而下游會把它讀成「不存在」。要宣告不存在,先加密網格。

### [asymmetric-samples] 兩邊的樣本大小不一樣,而小的那邊剛好是支持行動的那邊  (原 5.29)

一個 peer 量了一個機制該不該修,給了兩組數字:

    健康配置「不要修」的證據    **12 顆種子**   → −1.50pp
    壓力配置「它幫忙」的證據     **4 顆種子**   → +3.9pp

**兩組數字各自都是誠實的量測。錯誤只存在於兩者的比較裡。**
把壓力配置補到同樣的 12 顆種子之後,那個 +3.9pp 變成 −0.33pp
(種子之間的散布是 68–84%,所以 0.3 完全在雜訊裡)——**效果消失了**。

值得注意的是它的**方向**:鬆的那一組出現在「**支持動手**」的那一邊。
這不是巧合的偏誤形狀——一個看起來支持你想做的事的結果,比較容易被當成「夠了」而停下;
一個擋住你的結果,你會再跑一輪確認。**於是嚴謹度會沿著你的偏好分布。**

這是 SKILL.md 第六節(兩端要來自同一支儀器)的**樣本大小版**:那一節講方法、origin、區間、時點,
這一條講**證據的量**。同一支探針、同一個配置,只是一邊跑了 12 次一邊跑了 4 次,
比較就已經不成立了。

**判準,兩個都要:**

1. **比較兩個 arm 之前,先把它們的樣本數寫在同一行。** 不一樣就先補齊再比。
2. **問「哪一邊拿到比較鬆的儀器?」如果那一邊剛好是你想要的結論,先補那一邊。**

⚠ 這件事被抓到不是因為有人稽核樣本數,是因為我為了別的理由提醒它
「取樣要取在不足那一段」——**它補完之後把自己的結論翻掉了**。
**沒有人在看樣本數的對稱性**,它不會自己浮出來。

附帶:同一個 peer 在同一封信裡寫過「`bigPct` 是分岔後的比例,不能當配對對照」,
然後在下一段引用了 `bigPct` 54.0% → 63.2% 當證據。
**寫下一條規則跟遵守它之間,還隔著一次自我檢查。**

### [wrong-criterion] 修一個實例只是把它推給下一個 → 判準取錯了,不是資料錯了  (原 5.25)

我寫了一條 guard:「任何鐘點的候選池不可以只剩一列事件」,並且派人去修唯一的違規。

peer 在 0.25 小時的格子上**暴力掃過全部 9,120 個可能的窗**,回報:符合的只有一個,
**而那個唯一解會讓另一列事件在另一個樓高接手當唯一候選**。同一個形狀換一個 id。

**它擋下來問我,而不是順手把第二列也改掉。** 那個判斷救了我一次:
如果它改了,我會看到全綠,而那條 guard 會繼續逼下一個人改第三列。

真正的錯在判準。「唯一候選」本身不是缺陷——**一棟小樓凌晨只有一列事件可以發生
是正常的**。有問題的是那一列因此吃掉 20.2% 的預算。換成「佔比 ≤ 15%」之後,
同一個 `hours` 窗單獨就解決了,**第二列一個字都不用改**。

**判準:當一個 guard 的修法是「再改一個地方」,而那個地方本來是好的,
先懷疑判準而不是資料。** 一條逼人打地鼠的不變式,通常是把「症狀」寫成了規則
——真正的規則在症狀後面一層,而且往往是連續量(佔比、比例、距離)而不是布林。

⚠ 附帶,同一趟我犯了 [true-sentence-wrong-scope]:peer 回報「頻率 20.1%」和「送達 −8.5%」兩件事,
我**只複驗了頻率**,然後寫下「它是對的」——一句話同時替兩個測量背書。
另一支 peer 用同種子成對、40 種子重跑,證明 −8.5% 掉在雜訊裡(每局標準差 85,
8 種子的雜訊就有 ±17%)。**而那個數字已經被我寫進 commit message 與 issue。**
**背書要逐項,不要用一句「它是對的」蓋過一組主張。**

## 主張與規格——句子本身騙人

### [true-sentence-wrong-scope] 一句正確的話,配上錯誤的適用範圍  (原 5.4)

測量是真的,句子是真的,**範圍是錯的**。因為測量真實,結論就感覺理所當然,
而且從句子內部看不出來。

例:「這個檢查不再能證明 SQL 字串一致」——真的,但讀者會自己補上一個
比事實大得多的範圍,然後去「修復」一個更好的設計。

**解法(適用於任何有界的主張,不只註解):**
> 在同一段話裡同時寫下「還證明得了什麼」和「不再證明什麼」。
> 光寫否定句,讀者會自己補上界線,而且補得比事實大。

這條同樣適用於 commit message、交接、issue 留言,以及 orchestrator 的
驗證報告——**「我沒驗到 X」如果不配上「我驗到了什麼」,一樣會誤導。**

### [report-is-a-reading] peer 的回報是一次讀數,不是樹的屬性  (原 5.18)

一個 peer 回報「be 把 BELT_SECONDS 從 v4 的 12 改成了 60」。**寫的當下是真的。**
我幾小時後讀到,把它當成當前狀態轉述出去,開了一個 issue 要求做一件**早就
做完**的修改,還把它當成一個活的決策拿去給 owner 裁決——於是 owner 用我沒
查證的資訊,對一個死掉的問題做了決定。另一個 peer 拒絕了這個前提,證明那個
常數從某個**我自己驗證並 land 過**的 commit 起就是 12。

有兩件事讓那個過期的說法顯得像現況:

- 它**具體而且有量測**。一張帶著 px/s 數字的表格,讀起來像系統的性質,不像
  某個時點的快照。
- **產品裡一段過時的註解在替它背書**(「density at BELT_SECONDS 60 puts 26
  items on the belt」)。唯一能糾正我的地方,反而在附和我。

**判準:轉述任何 peer 對「現況」的說法之前,自己去讀那個值。**
`git log -S` 會告訴你它上次變動是什麼時候。這件事只花幾秒,而且是這個說法
帶著你的名字送到 owner 面前之前的最後一道關卡。

**往上呈報不會洗白一個未經查證的前提**——它只是把你的錯誤,轉換成對方的
錯誤決定。

附帶一條:那張表格用「輸送帶秒數」當標籤,但真正決定答案的是**機器人數量**
(同樣 12 秒,一台是 1.4、四台是 4.2)。**標籤要寫出被固定住的變數**,因為
被引用出去的正是標籤,不是旁邊那段散文。

### [naming-is-not-scanning] 把 bug 寫成一個「類」,不等於掃過那個類  (原 5.17)

一個 peer 找到某條 guard 不可能紅。我複驗、證偽、寫進記憶、寫成本檔的一節、
推上公開 repo——然後宣布另一份 harness 全綠。**那份 harness 裡有一模一樣的
那一行**,而且我一小時前才在 issue 上引用過它的綠當證據。是另一個 peer
grep 出來的。

**把它「命名成一個類」的動作,感覺起來就是那個推廣的步驟**,所以真正推廣的
動作——去掃同一個形狀——從來沒有被排進待辦。寫得越完整,越有一種已經處理
完畢的感覺。

**判準:一個 bug 被命名成類的那一刻,下一個指令就是 grep,而且在寫心得之前
跑,不是之後。先掃自己的檔案**——你被告知的那個實例,是別人正在看的地方;
沒被掃到的副本,不成比例地落在沒有人會讀的區域裡。

同一趟要防反方向的錯:兩個 `splice(i, 1)` 命中同一個形狀而且是**正確的**
(移除元素、本來就不要回傳值)。掃之前先講出一個正確用法,掃才不會吃掉它。

### [lesson-not-self-applied] 你寫進每一份 brief 的那條教訓,你自己的檔案掃過了嗎  (原 5.23)

[naming-is-not-scanning] 說「把一個 bug 命名成一個類,不等於掃過那個類」。這是它的加強版:
**當你把一條教訓寫進派給別人的 brief 時,那條教訓就變成了一個規格,
而你自己的檔案是否符合它,你從來沒有查過。**

我在 exp / roof 兩帶每一份 brief 裡寫了第 13 條:「**在原始碼文字上比對會把
註解當資料。用解析後的表,不要用 grep。**」而我自己 harness 的第 11 組是
`SIM_SRC.match(/codex\.(\w+)/g)`——**逐字就是那個形狀**。`sim.js` 有一行
註解在警告「不要共用 `codex.pairsDelivered`」,而那個 regex 把這句警告
讀成「有人寫得進去」。**擋住這條 guard 的,正是它所守護的那個危險的說明文字。**

實測:插一條 `test: s => s.codex.pairsDelivered >= 3`(一條物理上永遠拿不到的
成就),**整份 harness 69 pass / 0 fail**。修好之後才看到洞有多大——
**不是一個鍵,是三個**(`xxx`、`pairsDelivered`、`onTime`),三個都來自
「解釋這個危險」的文字。

而且同一天,我在調查這件事的時候**又用 grep 去掃 `at:'any'` 的事件**,
掃出一個空集合,而 `powersurge` 明明就有。**我在寫那條教訓的中途違反了它。**

**判準:一條教訓寫進 brief 的那一刻,先對自己的檔案跑一次。**
派工的動作會讓你覺得那條教訓已經「處理掉了」——它只是被轉發了。

### [size-not-hit-target] 尺寸不是點擊目標:規格寫了容易斷言的那個屬性  (原 5.19)

手機版面通過了 engine 33/0、acceptance 39/0,其中包含一條專為我寫的驗收條件
新增的 guard:

> 每個點擊目標在兩軸都要 ≥ 32px。**要斷言,不要用眼睛看。**

那些分頁**確實是** 63×52。斷言是真的。但抽屜的把手——寬度跟著地板欄位走、
停在它的底緣——蓋住了六個分頁裡的前四個,包含「機器人」。**在手機上買不了
機器人。** 我是靠截圖發現的,而在那之前這個專案沒有人成功截過圖。

**尺寸是元素自己的屬性;可及性是元素「加上所有在它之後繪製的東西」的屬性。**
一條量前者的 guard 永遠看不到後者。而我知道量後者的方法——`elementsFromPoint`
在更早的兩個 issue 就是為了這件事用的——我還是寫了比較弱的那一條。peer 正確
地實作了我的條件,所以那個綠是誠實的,而且沒有用。

**判準:斷言應該是「這個元素是不是它自己中心點上最上層的東西?」**,在每一個
支援的寬度上跑。**一顆被遮住的 63×52 按鈕,對拇指而言是 0×0。**

更一般的形式:**當規格點名一個「尺寸」,先問真正決定結果的屬性是什麼。**
尺寸容易斷言,而那正是它會被寫進規格、真正的性質不會的原因。

路上的陷阱:在**暫停**的頁面上,`elementsFromPoint` 每一點都回傳暫停遮罩,
於是「全部元素都不可及」——一個非常有說服力的假陽性。這次那個遮罩的 class 是
`on`、只有 **id** 是 `veil`,所以 `.veil` 選擇器抓不到它;我就寫了一條,然後
短暫地得到一個嚴重得多、而且完全錯誤的結論。先用 id 把遮罩關掉,再做命中測試。

### [no-scroll-not-fits] 「沒有捲軸」不等於「裝得下」——被丟掉的溢出量得更好看  (原 5.20)

需求是「整個遊戲要塞進手機、最好不用捲」。我量到
`documentElement.scrollHeight === innerHeight`、零個內部捲軸、**任何數量都一樣**,
差點回報需求已達成。

它達成的方式是:**地板把裝不下的東西直接丟掉。** iPhone SE 上畫出 5 格,
玩家實際擁有最多 40 台,其餘畫在畫布外。不是「捲下去看得到」,是不存在。
過了第五台,玩家就修不了壞掉的機器人——而那是遊戲兩個動詞之一。

**關鍵在於「裝得下」和「溢出被丟掉」從每一個捲動指標看都完全相同,而且
丟掉的那個版本分數更好看。** 任何用 `scrollHeight`、重疊、或「沒有東西在
畫面外」建起來的 guard,兩者都會通過。

**判準:視窗容納類的需求,要斷言的是「畫了幾個」對「擁有幾個」**,由渲染器
自己公布。而且**被丟掉的數量要從每個項目的幾何算出來,不要從那個 skip 的
迴圈算** —— 一個不再 skip 的版本會把東西畫到邊界外,而它仍然必須回報那些是
被丟掉的。

同一天學到的下半段:**會數數的 guard 不會判斷。** 縮到 32×26 之後 40 個全部
塞得下,整套 **52/0 全綠**——而那個版面的名牌只有 4px 高、40px 高的圖形放進
34px 的列距、每個下緣壓進下一格的命中區 6px,於是**畫面和命中區不一致**。
把「裝得下」和「裝得下而且能用」分開的,只有一張截圖。

## 通道與協作

### [dispatch-not-delivered] 派工回報成功,不代表對方收到  (原 5.11)

**整份 skill 假設派工會到。它不一定會到。**

通常有兩條通道,而它們的行為完全不同:

| 通道 | 送到哪裡 | 對方沒在跑的時候 |
|---|---|---|
| peer 訊息 / agent 佇列 | 對方的 **agent loop** | **永遠不會排空**,訊息不會出現在它的 transcript |
| session 訊息 | 以**使用者回合**送達 | 會喚醒 interactive session |

`success: true` 常常只代表**名字解析到一個可達的 agent**,不代表送達。

而且這個陷阱**自帶一個假的證偽**:拿一個不存在的名字去送、被拒絕,看起來
像是證明了通道會動。它只證明了**位址解析**。這正是 [true-sentence-wrong-scope]——一句正確的話,
配上比事實大的適用範圍。

**判準,兩個都要:**

1. 先看對方的 **`isRunning`**。沒在跑的 session 不會處理任何東西。
2. 派工之後,**去對方的 transcript 搜尋你自己訊息裡的一個特徵字串**。搜不
   到就是沒送到,不管回報說什麼。

**在確認送達之前,不要開始等。** 真實案例:九則訊息、兩小時、三次「他們
開工了嗎」的檢查,全部在一條靜默不送達的通道上;`isRunning: false` 從第一
分鐘就在那裡,只是沒有人去看。

**回程有同樣的病,解法在 SKILL.md 第三節「回程」**:不要要求 peer 宣告,要求它留下痕跡,
再放一個哨兵把痕跡變成叫醒你的事件。

### [diagnosis-outlives-validity] 診斷正確,但活得比有效期久  (原 5.13)

[dispatch-not-delivered] 的鏡像,而且更難看見:**通道修好之後,你可能還在照著它壞掉時的假設行動。**

真實案例。前九則派工確實沒送到——用錯通道,而且我查證過(對方 transcript
裡搜不到)。診斷正確。接著我換了通道,**新通道每一次都成功**,三次全中,
訊息也確認進了對方的 transcript。

但我把舊結論帶著走,繼續回報「它們停擺了,請 owner 去戳一下」——**在我
手上已經有能叫醒它們的機制之後**。舊結論沒有被任何新證據推翻,它只是
**沒有被重新檢查**。

還有一半的錯是誤讀對方的狀態:interactive session 是**一則輸入換一個回合**,
做完就停下來等。那不是卡住,是正常結束。我把「回合結束」讀成「掛掉」,於是
把一個我自己能解的問題往上報。

**判準,兩條:**

1. **修好一個機制之後,回頭把所有「因為它壞掉」而下的結論標記為待重驗。**
   問一句:「這個結論當初成立的前提,現在還成立嗎?」
2. **對方「安靜」時,先分清楚是「壞了」還是「做完了在等」。** 前者要修,
   後者只要再給它一則輸入。而每一則訊息只買得到**一個回合**,所以每一則
   都要裝得下一個完整的工作單位。

把「請 owner 去戳」當成解法之前,先確認那真的不是你自己能做的事。
